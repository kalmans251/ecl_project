# 선택 레이더 실시간 좌표

## 동작

기존 모니터링 메인 화면의 레이더 캔버스를 사용한다. 난간 **하나**를 선택하고 레이더 화면을 열면 로그인 세션으로 `/ws/operator/radar/<난간 UUID>`에 연결한다. 일반 상태조회는 기존 2초 주기를 유지한다. 좌표는 별도 WebSocket으로 전달되며 `reported`에 저장하거나 좌표마다 DB 기록을 만들지 않는다. 개발자 도구에서는 해당 WebSocket의 Messages에서 `targets`를 확인한다.

- 앞뒤 레이더의 기존 사람 감지·누적 카운트 로직은 변경하지 않는다.
- 좌표는 S3의 `RADAR_POSITION_SOURCE`로 선택한 센서 하나만 사용한다. 웹에는 `레이더 1/2`를 표시한다. 번호와 실제 앞/뒤 설치 방향은 현장 배선에 맞춰 확인한다.
- S3는 선택 센서의 최신 좌표를 200ms 간격으로 **WROOM → P4 내부 구간에만** 전달한다. 사람 없음도 보내며 통화 중에는 기존 정책대로 중단한다. PLC로 임의 송신하지 않는다.
- P4는 최신 상태 하나만 보관한다. 1.5초 이상 새 관측이 없으면 `available=false`로 응답한다. 현재 대상이 있다가 0명이 되는 전환은 3개의 연속된 S3 샘플로 확인한다. 이 과정은 누적 감지 이벤트를 만들지 않는다.
- Pi는 웹에서 보는 난간에만 조회한다. 대상 없음/미확인일 때는 약 2초 간격으로 **좌표 없는 짧은 상태 조회**를 한다. 사람이 나타나면 좌표 조회로 전환한다.
- 대상이 있는 동안에는 응답 후 500ms 간격으로 좌표를 요청한다. 정지한 사람도 조회하며 이동량에 따른 가변 주기는 사용하지 않는다.
- 여러 난간을 여러 사용자가 보면 Pi 한 작업이 순서대로 처리한다. 같은 난간을 보는 사용자가 여러 명이어도 PLC 조회는 중복 생성하지 않는다. 요청 사이 전체 최소 200ms 간격을 둔다. 다른 명령/음성/음악/이벤트 처리와 버스 잠금을 공유하므로 실제 주기는 지연될 수 있다. 2Hz 실시간 보장은 아니다.
- 통화·비상·미확정 통화 상태에는 좌표 요청을 하지 않는다. 완료 후 현재 대상 유무부터 다시 확인한다.
- 응답 타임아웃은 0명으로 간주하지 않는다. 최신 좌표가 없으면 점을 지우고 미수신/현재 위치 미확인 상태를 표시한다.
- 화면 숨김/닫기/다중 선택 시 연결을 닫는다. 서버는 최대 약 2초 뒤 수요를 갱신한다. 서버 연결이 끊기면 Pi의 6초 조회 임대가 만료된다. 관측은 S3–P4 내부에서 계속 유지한다.

최초 감지 표시는 상태조회 간격(최대 약 2초), 요청/응답, 버스 대기시간이 더해진다. 빠른 움직임의 궤적 기록 또는 앞뒤 전체 인원 위치를 보장하는 기능이 아니다.

## 적용

1. 같은 변경의 **ESP32-S3와 P4 펌웨어**를 빌드하고 업로드한다. WROOM은 기존 중계 코드를 그대로 사용한다.
2. 난간 Pi 코드를 업데이트하고 기존 `main.py --monitor-url ...` 실행 명령으로 다시 시작한다. 별도 레이더 프로세스/시리얼 리더를 실행하지 않는다. `--event-railings`에는 설치된 난간 번호를 포함한다.
3. Spring Boot 업데이트 후 재시작한다. DB 삭제나 토큰 변경은 필요 없다.
4. 기존 Nginx `/ws/` WebSocket 프록시 설정을 유지한다.
5. 웹에서 Ctrl+F5 후 메인 모니터링 화면에서 난간 하나를 선택하고 레이더 화면을 연다. 기존 UI의 레이더/CCTV 전환은 감지 모드 변경 준비도 수행하므로 실제 정책 변경은 기존 전체 적용 절차를 따른다.

기능 테스트 전용 페이지에는 새 캔버스를 추가하지 않았다. 현재 좌표는 메인 화면에서 확인한다. 누적 감지 횟수와 화면의 현재 대상 수는 다르다.

## 프로토콜 v1

Pi → P4: `SERVICE_RADAR(04) / STATUS_REQUEST(10)`, payload 5바이트:
`request_token:u32 BE | detail:u8 (0=대상 유무, 1=좌표 포함)`.

P4 → Pi: `SERVICE_RADAR(04) / STATUS_RESPONSE(11)`:
`token:4 | version=1:1 | sensor:1 | valid:1 | count:1 | observation_seq:4 | age_ms:2 | detail:1 | XY:count*4`.

`XY`는 detail=1이고 valid=1일 때만 포함한다. X/Y는 signed int16 BE mm, Pi에서 m로 변환한다. 센서번호 0은 아직 샘플을 받지 못한 상태에만 해당한다. 응답 순번은 P4 수신 샘플 순번으로 재부팅 시 초기화된다. Pi는 전역 증가 순번 대신 난간/출발지/목적지/서비스/명령/요청 토큰으로 응답을 매칭한다.

서버는 로그인·동일 출처·현장 접근 권한을 확인하며 전송 전 권한을 다시 확인한다. 게이트웨이 입력은 현재 연결과 등록된 난간 번호로 범위를 제한한다. 좌표는 메모리에만 잠시 보관한다. 브라우저는 유효기간이 지나면 마지막 점을 제거한다.

## 검증 범위

Python 자동 테스트: 요청 매칭, 통화/잠금/임대 만료 시 무송신, 타임아웃 구분, 음악 메시지와 공존.
P4 실제 C 소스 호스트 테스트: 비연속 슬롯 좌표 압축, 센서 구분, 0명 연속 확인, 캐시 만료, 응답 구조.
Java 테스트: 좌표 검증, 게이트웨이/난간 격리, 현장 권한, 중복 구독의 단일 조회 수요, 오래된 데이터 거부.
브라우저 테스트: 난간 전환 후 이전 응답 무시, 숨김 시 중단, 재연결, 점 만료.

실제 PLC/레이더 연결과 펌웨어 업로드 후 이동 반응성 검증은 별도 필요하다. 전체 ESP-IDF/PlatformIO 빌드는 저장소 CI에서도 확인한다.
