# 슬립 전환 후 프로젝터 상태 갱신

슬립 진입 또는 사람 감지 후 복귀로 실제 프로젝터 출력이 바뀌면,
Pi는 다음 정기 전체 상태 조회를 기다리지 않고 해당 난간의 상태 조회를 우선 예약합니다.

## 처리 순서

1. P4는 기존 EVENT_POLL의 빈 응답에 실제 sleep_active와 프로젝터 GPIO 출력 상태를 덧붙입니다.
2. Pi는 난간별 이전 값과 비교합니다. 최초 응답 또는 값이 바뀐 경우 StatusSync.refresh를 호출합니다.
3. 조회 작업 스레드가 기존 제어 잠금과 PLC 통신 순서를 지키며 상관 식별자가 있는 전체 상태를 요청합니다.
4. 실제 응답을 받은 뒤 기존 telemetry 경로로 서버에 전달합니다. 웹은 기존 상태 갱신 때 이를 표시합니다.

변화 알림 자체를 실제 전체 상태로 저장하거나 ON/OFF 선택값을 덮어쓰지 않습니다.
웹이 해당 난간을 보고 있지 않으면 추가 전체 상태 조회를 하지 않습니다.
비상 호출 및 통화 종료/오류 응답이 있으면 기존 응답을 먼저 보내며, 출력 변화는 이후 빈 응답에서 확인합니다.
여러 번 바뀐 경우 중간 동작 이력 대신 최신 상태를 확인합니다.

## 프로토콜 호환성

기존 8바이트 EVENT_POLL 요청은 그대로입니다.
이벤트가 없는 EVENT_REPLY는 기존 14바이트 또는 확장 16바이트를 Pi에서 허용합니다.

| payload 위치 | 의미 |
| --- | --- |
| 0~13 | 기존 토큰, 이벤트 ID=0, 유실 수, 서비스=0, 명령=0 |
| 14 | 실제 슬립 출력 정지 상태: 0/1 |
| 15 | 프로젝터 GPIO 출력 상태: 0/1 |

CRC와 요청 토큰 검증은 유지합니다. 최대 이벤트 응답은 여전히 34바이트(프레이밍 포함)라 기존 통신 예산을 늘리지 않습니다.
이 값은 외부 프로젝터의 광출력 센서값이 아니라 P4의 릴레이 제어 출력 상태입니다.

## 적용

Pi 코드를 먼저 업데이트하고 게이트웨이를 재시작한 뒤 P4 펌웨어를 업데이트합니다.
WROOM/S3 및 서버 변경은 필요 없습니다. 웹은 기존 슬립 상태 갱신 로직을 사용합니다.
기존 P4에서는 기존 정기 조회로 계속 동작합니다.

이는 비동기 무제한 송신이 아닙니다. 이벤트 순회, 다른 난간 수, 통화 우선 제어,
PLC 왕복 및 브라우저 조회 주기에 따른 지연은 남습니다. 실제 현장 지연은 별도 확인해야 합니다.
